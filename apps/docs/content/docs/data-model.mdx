This is the SQLite schema the iOS app starts with. Postgres on the server holds the same tables, as [tech stack](/docs/tech-stack) explains. The words used here are the ones defined in `GLOSSARY.md`.

This page is a draft. Nothing is built yet.

## Rules every table follows

Every table that holds your data has the same three columns, so sync can treat all of them the same way.

| Column | Type | What it is |
| --- | --- | --- |
| `id` | text | Made on the phone, so rows never need the server to get an ID. Usually a random UUIDv7. See below for the rows that build it from their contents. |
| `updated_at` | integer | Milliseconds since 1970. Set on every change. When the same row changed on two devices, the later one wins. |
| `deleted_at` | integer, nullable | Set instead of deleting the row, so the deletion syncs like any other change. |

On the server, every row also has a `user_id` and a sync cursor. The phone does not store either.

Some rows must be unique, and a random ID can't guarantee that. Two phones offline would each make their own row, and sync would keep both. These rows build their ID from what makes them unique instead, as a UUIDv5 of the parts listed. Two phones then produce the same ID, and sync merges them like any other edit to one row.

| Table | ID built from |
| --- | --- |
| `user_setting` | The account ID |
| `exercise_brand`, no-brand row only | The exercise ID |
| `workout_exercise_setting` | The workout exercise ID and the setting ID |
| `workout_set_override` | The set ID and the setting ID |
| `routine_exercise_setting` | The routine exercise ID and the setting ID |
| `routine_set_override` | The routine set ID and the setting ID |

- Weight is always stored in kilograms. A setting picks whether you see and type kg or lb.
- Durations are stored in whole seconds.
- Order within a list is a `position` number. When you drag an exercise between two others, it gets the number halfway between theirs, so a reorder changes one row and not the whole list. After many drags between the same two rows the gap gets too small to halve, so when that happens the app renumbers that one list.
- Deleting a row also sets `deleted_at` on every row under it in the same transaction. Deleting a workout marks its exercises, setting values, sets and overrides deleted too, so any table can be read without checking its parents.

## Exercises and brands

```
exercise ──< exercise_brand ──< setting
    └──< exercise_muscle
```

**`exercise`**

| Column | Type | Notes |
| --- | --- | --- |
| `name` | text | Such as "Chest Press" or "Dumbbell Flies" |
| `equipment` | text | |
| `is_builtin` | integer | 1 for the built-in list |

Built-in exercises ship with the app and have fixed IDs, so they are the same on every phone and never sync. The server is seeded with the same rows and IDs, so synced rows that point at a built-in exercise still pass its foreign keys. Custom exercises are ordinary rows.

Deleting a custom exercise sets `deleted_at` on it, its `exercise_brand` rows, their settings and its `routine_exercise` rows (with their sets), in one transaction. Its `workout_exercise` rows are left alone, so finished workouts still show it with their sets, and the exercise page and stats keep its history. Only rows without `deleted_at` show in the picker and the library. Because `name` is unique, creating an exercise with a deleted one's name clears `deleted_at` on that row instead of adding another, which brings its history back with it.

**`exercise_muscle`**

Which muscles an exercise works, and how much of the work each one does. A future fatigue meter needs this per muscle, and it can't be filled in for old exercises after the fact.

| Column | Type | Notes |
| --- | --- | --- |
| `exercise_id` | text | |
| `muscle` | text | From the fixed muscle list below |
| `share` | real | Above 0, up to 1. The primary muscle is 1 |

- An exercise has at least one row, and exactly one with a share of 1.
- The muscle list is fixed in the app and on the server: `abdominals`, `abductors`, `adductors`, `biceps`, `calves`, `chest`, `forearms`, `glutes`, `hamstrings`, `lats`, `lower back`, `middle back`, `neck`, `quadriceps`, `shoulders`, `traps`, `triceps`. It matches free-exercise-db, which the built-in list is seeded from.
- Muscles belong to the exercise, not the brand. A different brand of chest press still works the chest.
- A custom exercise gets a share of 1 for its primary muscle and 0.5 for each secondary muscle. The shares can be edited later.

**`exercise_brand`**

One row for each brand you have used for an exercise, plus one for no brand if you have logged it without one. Technogym chest press and Hammer Strength chest press are two rows. Settings, sets and records all hang off this row.

| Column | Type | Notes |
| --- | --- | --- |
| `exercise_id` | text | |
| `brand` | text, nullable | Empty means no brand. Otherwise plain text you typed or picked |
| `label` | text, nullable | The model, the gym, or anything else that tells two of the same brand apart |

- Brand and label together pick the row. Technogym with the label "City gym" and Technogym with no label are two rows, each with its own settings, history and records. Clearing the label goes back to the row with none. The app shows the two as "Technogym · City gym" and "Technogym".
- Logging an exercise without picking a brand uses its no-brand row, and creates it the first time. An exercise has at most one no-brand row.
- When you add an exercise to a workout, the app defaults to the row you used last time.
- The built-in brand list only feeds the suggestions when you type one.
- Renaming a brand changes `brand` on its row, so its settings, sets and records come along for free. That is also how no-brand history moves onto a brand you add later.
- Moving history onto a brand that already has a row merges the two in one transaction: the workout and routine exercises point at the destination row, a setting both rows have (by name) keeps the destination's definition and next-time value with the source's past values re-pointed at it, a setting only the source has moves over with its values, and the source row and its merged settings get `deleted_at`. Picking the merged-away brand again revives its row.
- Renaming a brand edits this row, so the history comes with it. Adding a brand to the no-brand row works the same way.

**`setting`**

Seat height, notch, dead stop and anything else you set up on this exercise and brand.

| Column | Type | Notes |
| --- | --- | --- |
| `exercise_brand_id` | text | Settings never carry over between brands |
| `name` | text | Such as "Notch" or "Dead stop" |
| `kind` | text | `number`, `yes_no` or `text` |
| `value` | real, nullable | The value filled in next time, for `number` and `yes_no`. A yes/no stores 1 or 0 |
| `text_value` | text, nullable | The same, for `text` |
| `direction` | text, nullable | `higher` or `lower`. Set only on a tracked `number` setting |
| `range_min` | real, nullable | Required when `direction` is set |
| `range_max` | real, nullable | Required when `direction` is set, and above `range_min` |
| `split_by_value` | integer | 1 gives each value its own progress |
| `factor` | real, nullable | For `yes_no` only: how much harder the set is when it's on, above 1 and at most 2, such as 1.5 for a dead stop. Null means it doesn't count (ADR 0002) |
| `position` | real | The order on the settings line and in headings |

- `value` and `text_value` are what the app fills in the next time you add this exercise on this brand. Finishing a workout copies the values it used back here, and so does editing them from Edit exercise.
- These are only defaults. What a past workout used lives in `workout_exercise_setting`, so changing a setting's value never changes history.
- Rows refer to a setting by its ID, never its name, so renaming a setting keeps every value and override.

## Workouts and sets

```
workout ──< workout_exercise ──< workout_set ──< workout_set_override
   │          └──< workout_exercise_setting
   └──< workout_media
```

**`workout`**

| Column | Type | Notes |
| --- | --- | --- |
| `started_at` | integer | |
| `finished_at` | integer, nullable | Empty while the workout is running |
| `routine_id` | text, nullable | The routine it was started from, if any |
| `note` | text, nullable | |
| `import_key` | text, nullable | Where an imported workout came from, such as `hevy\|13 Nov 2025, 07:30\|Push`. Its `id` is a UUIDv5 of this, so importing the same file again finds the row. Empty for workouts logged here |
| `gym_name` | text, nullable | Where the workout was done, such as "City Gym" or "Home". Empty when you didn't say |
| `gym_address` | text, nullable | The gym's address, when it was picked from the map |
| `gym_latitude` | real, nullable | Where the gym is, when it was picked from the map. Empty for a typed name |
| `gym_longitude` | real, nullable | As above |

At most one workout has no `finished_at`. That is the one the app opens into. If a pull brings in a second running workout, because you started one on each phone while offline, the app keeps the one with the most recent ticked set open and finishes the other at the time of its last ticked set. Nothing is deleted.

**`workout_exercise`**

| Column | Type | Notes |
| --- | --- | --- |
| `workout_id` | text | |
| `exercise_brand_id` | text | Gives both the exercise and the brand |
| `position` | real | |
| `rest_seconds` | integer | |
| `note` | text, nullable | |

**`workout_exercise_setting`**

The value each setting had for the whole exercise in this workout: the line under the exercise's name.

| Column | Type | Notes |
| --- | --- | --- |
| `workout_exercise_id` | text | |
| `setting_id` | text | Must belong to the same exercise and brand as the workout exercise. The app checks this before saving |
| `value` | real, nullable | For `number` and `yes_no`. A yes/no stores 1 or 0 |
| `text_value` | text, nullable | For `text` |

- Adding an exercise to a workout copies the setting's current value into a row here, so the line is filled in from last time.
- A row with no value means the setting was there but left empty in this workout.
- A setting added after a workout was logged has no row in that workout.

**`workout_set`**

Not called `set`, because `SET` is a reserved word in SQLite and every query would have to quote it.

| Column | Type | Notes |
| --- | --- | --- |
| `workout_exercise_id` | text | |
| `position` | real | |
| `kind` | text | `reps` or `hold` |
| `set_type` | text | `normal`, `warmup`, `drop` or `failure`. Defaults to `normal` |
| `weight_kg` | real, nullable | Empty means unloaded, which is not 0 kg |
| `reps` | integer, nullable | Rep sets only |
| `duration_seconds` | integer, nullable | Holds only |
| `rpe` | real, nullable | 6 to 10 in half steps |
| `completed_at` | integer, nullable | Set when you tick the set |

The values can be empty while you are still typing. Once a set is ticked, a rep set must have reps and no duration, and a hold must have a duration and no reps.

Warm-up sets never count toward records or scores. Drop sets and sets to failure count like normal sets, and the type is kept so a fatigue meter can weigh them differently later.

**`workout_set_override`**

A value that a group of sets changes from the exercise's value, such as notch 8 on the holds while the rest of the sets use notch 7.

| Column | Type | Notes |
| --- | --- | --- |
| `workout_set_id` | text | |
| `setting_id` | text | Must belong to the same exercise and brand as the set. The app checks this before saving |
| `value` | real | A yes/no stores 1 or 0. Text settings can't be overridden |

- A set has at most one override per setting.
- Every set in a group carries the same overrides. Groups aren't stored: the app draws a new heading wherever the kind or the overrides change from one set to the next.
- A set's value for a setting is its override if it has one, otherwise the exercise's value in `workout_exercise_setting`. Scores and records read this value.
- If neither has a value, the set has no value for that setting, and that is what gives it a different shape from sets that do.

**`workout_media`**

A photo or video kept with a workout, such as a form check or a picture of the machine's settings.

| Column | Type | Notes |
| --- | --- | --- |
| `workout_id` | text | |
| `kind` | text | `photo` or `video` |
| `file_name` | text | The row's ID plus the file's extension, such as `7A1C….heic` |
| `width`, `height` | integer, nullable | Pixels, the right way up |
| `duration_seconds` | real, nullable | Videos only |
| `created_at` | integer | When it was added |

- The file itself lives in Application Support under `media/`, with a thumbnail made once in `media/thumbnails/`. Neither is in Caches, so the system never clears them.
- For now the files stay on the phone. The row syncs like any other, but uploading the file to the server and showing it on a second phone is a follow-up that needs storage behind the API.

## Routines

```
routine ──< routine_exercise ──< routine_set ──< routine_set_override
              └──< routine_exercise_setting
```

| Table | Columns |
| --- | --- |
| `routine` | `name`, `position` |
| `routine_exercise` | `routine_id`, `exercise_brand_id`, `position`, `rest_seconds`, `note` |
| `routine_exercise_setting` | `routine_exercise_id`, `setting_id`, `value`, `text_value` |
| `routine_set` | `routine_exercise_id`, `position`, `kind`, `set_type`, `weight_kg`, `reps`, `duration_seconds` |
| `routine_set_override` | `routine_set_id`, `setting_id`, `value` |

The setting tables work like their workout versions. Starting a workout copies these rows into new `workout_exercise`, `workout_exercise_setting`, `workout_set` and `workout_set_override` rows. A setting the routine has no row for takes the setting's current value. Changes made during the workout never reach the routine.

## Settings

| Table | Columns |
| --- | --- |
| `user_setting` | `weight_unit` (`kg` or `lb`) |

There is one row per account. It syncs, so a second phone gets the same unit.

## On the phone only

These tables never sync.

| Table | What it holds |
| --- | --- |
| `sync_outbox` | Rows changed since the last push. Each row is the table name and the row ID. |
| `sync_state` | The cursor from the last pull. |
| `record` | The best weight, reps, time, tracked setting value and score for each exercise, brand and shape, with the set it came from. For a setting with its own progress per value, the value is part of the key, so notch 7 and notch 8 keep separate records. Rebuilt from the sets when a workout is saved, when a setting's range, direction or own progress per value changes, and after a pull that brought in sets, setting values or overrides. |

Records and scores are worked out from the sets, so they are never synced and two devices cannot disagree about them. [ADR 0001](https://github.com/AGroupForCoders/Fatigue/blob/main/docs/adr/0001-combined-set-score.md) explains the score.

## Still open

- **Changing the brand mid-workout.** The app swaps in the new brand's settings and keeps the logged sets. In the database, that means replacing the `workout_exercise_setting` rows and dropping overrides whose setting isn't on the new brand, even on sets already ticked. The other option is to only allow the switch before any set is ticked.
- **Deleting a setting.** Proposed: the setting is marked deleted and its values and overrides in past workouts stay, so history and records don't change. It stops showing on new workouts. During a running workout the app already drops its overrides, which matches.
- **Splitting shoulders.** The muscle list has one `shoulders`, which mixes front delts (pressing) with rear delts (pulling). A fatigue meter would want them apart. Splitting later means deciding the split for every exercise that uses `shoulders`, so it is cheaper to decide before the built-in list is seeded.
- **Merging duplicates.** Two phones could each add Technogym to adductors while offline, giving the same exercise and brand twice. Allowed in v1. The brand merge above fixes it by hand; whether sync should merge them automatically is still open.
